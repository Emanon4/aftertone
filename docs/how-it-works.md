# 推荐流程

```
起点歌曲 ─► 召回（≤5,000）─► 显式条件过滤 ─► 资料预排序（默认 600）─► 模型逐首评分 ─► 去重 / 每艺人一首 ─► 两组 × 7 首
```

1. **召回**：读取最多 10 个曲库分片（≤20,000 行），与起点艺人的电台、关联艺人热门曲合并，按方向配比抽样出最多 5,000 首可试听、未被排除的录音。
2. **显式条件**：补充偏好里的“不要现场版 / 不要混音 / X0 年代”直接过滤；「不太合适 → 不喜欢这位歌手」累计的艺人在这里排除。
3. **预排序**（`lib/server/prerank.ts`）：按来源（艺术家电台、关联艺人、曲库关联/邻近）、与起点共享的风格/策展分组、年份与 BPM 接近程度打分，取高分部分，并按方向保留 10% / 20% / 35% 的随机探索名额，防止只推“资料多”的热门曲。
4. **评分**：每首候选单独提问（有补充条件时再加一个条件问题），模型只能看到资料，提示词明确禁止推断旋律、音色或情绪。任何一批缺失、越界或格式错误都会让整轮停止，不展示部分结果，也不自动重试付费批次。
5. **呈现**：按分数排序，每位艺人只取一首，最多 14 首分两组。推荐理由由资料生成，例如「Men I Trust 的关联艺人 · 同属「独立」 · 年代相近（2020）」；模型返回的文字理由一律不展示。

## 为什么是 600 首

旧版每轮把 5,000 首都交给模型，其中大半是随机抽样的曲目，却要消耗约 160 万输入 token。先用免费的资料关联筛到 600 首，评分成本约降到 1/8，探索名额保证仍有意外之喜。`CANDIDATE_LIMIT` 可调。

### 实测（2026-10-07，真实 Jev 评分）

**600 vs 5,000**（7 个起点，“沿着喜欢”，每个起点对完整召回池评分一次再推算两种结果）：入选歌曲平均分 1.707 → 1.683（−1.4%），最终 14 首平均重合 7.3 首；预排序后的 600 首里合格比例约是全池的 3 倍。重合度偏低主要因为合格歌曲常有几百首、分数接近，平均分更能反映质量。结论：保留 600。

**两处修复后**（只对线上实际评分的 600 首重新打分）：

| 起点 | 合格（/600） | 最终入选 | 入选平均分 |
| --- | --- | --- | --- |
| 周杰伦《晴天》 | 1 → 459 | 1 → 14 | 1.71 → 1.83 |
| Sade | 29 → 75 | 14 | 1.756 → 1.836 |
| Men I Trust | 168 → 413 | 14 | 1.773 → 1.819 |

1. **无分组的起点**：39% 的艺人（含周杰伦）没有策展分组，召回只能随机读分片。现在依次使用：离线推断的分组（`scripts/infer-artist-groups.mjs`，按专辑风格与歌名文字，补了 2,239 位）→ Deezer 实时相似艺人的分组投票 → 歌名文字。
2. **给模型的证据**：候选来源原来是中文短标签（如“艺术家电台”），模型没有把它当作“有记录的艺人关联”。现在改为英文的明确描述；起点专辑没有风格时，提供“相关艺人专辑风格”（`relatedArtistAlbumGenres`，字段名即说明来源）。

## 防滥用

- 写请求必须带允许的 Origin；没有 Origin 的脚本只能读。
- 可选 Turnstile 人机验证。
- 每个访问者每日轮数（IP 加盐哈希，每日轮换，不存原始 IP）。
- 个人 OpenAI 兼容 Key 在召回前先调用免费的 `/models` 校验，明确 401/403 直接拒绝；所有个人 Key 共享一个全局每日上限。
- 任务轮询只读，只有过期或租约失效时才写 D1。

## 曲库

```sh
python3 scripts/rebuild-library.py --manifest data/catalog-manifest.json --output output/rebuilt-catalog
node scripts/import-library.mjs output/rebuilt-catalog      # 导入后自动转换为 v3 紧凑格式
node scripts/enrich-albums.mjs --sample 200                # 先抽样看覆盖率，不改曲库
node scripts/enrich-albums.mjs --rate 5                    # 补齐全部专辑的年份与风格（可断点续传）
node scripts/infer-artist-groups.mjs                       # 为没有策展分组的艺人推断分组（存为 inferredGroups）
```

**v3 紧凑格式**（`scripts/compact-catalog.mjs`）：每个分片是 `{albums, tracks}`，歌曲行为 `[id, 歌名, 艺人下标, 专辑下标, 时长, 分组位掩码, 可试听]`，专辑行为 `[专辑 id, 专辑名, 封面哈希, 年份, 风格]`；艺人名在 `artists.json`，封面和歌曲链接由 ID 还原。转换时逐行还原比对，任何不一致都会中止。体积从 55MB 降到约 13MB，一次召回读取的 10 个分片从 8.2MB 降到 1.85MB。

**年份与风格**来自 Deezer `/album` 接口的发行日期和专辑风格，按专辑写入，所以“风格”是专辑风格而非单曲风格。全量 50,846 张专辑（2026-10-07）：年份 99.9%、风格 95.7%；56 张已不可用的专辑保持未知。按每秒 5 次请求约需 2.8 小时。

**预排序质量对比**：`TYPESAFE_API_KEY=... node scripts/compare-prerank.mjs --seeds 8`。模型对每首候选单独提问，所以每个起点只需对完整召回池评分一次，就能精确算出“只评 600 首”会选出什么；结果写入 `output/prerank-comparison.json`。按 2026-09 的基准，每个起点约 160 万输入 token。

有界采集公开元数据（最多 4 并发、3,000 次请求），不下载音频。后续扩库建议：

1. 在提供方条款允许的范围内，从已收录艺人的专辑补充非热门作品，再按语言、地区、年代补充新艺人，分别统计新增录音数与艺人覆盖。
2. 年份与专辑风格已补齐；ISRC 和版本信息仍缺。
3. 每批增量先检查字段来源、试听可用比例和重复录音，再用固定种子集比较收藏与跳过表现。
